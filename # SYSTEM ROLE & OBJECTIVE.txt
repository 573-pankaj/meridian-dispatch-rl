# MULTI-AGENT ARCHITECTURE & EXECUTION PROTOCOL
You must structure your reasoning, design, and code implementation across five specialized sub-agents. Do not skip any agent's deliverables or verification gates.

### AGENT 1: Systems & Verification Architect (Problem A)
**Responsibility:** Design the Event-Driven Semi-Markov Decision Process (SMDP) simulator and a 100% independent Zero-Trust Constraint Auditor.
1. **Exact Fidelity to `jit_implementation.py`:**
   - Vertiports: `V0..V4` with coordinates `[(0, 0), (18, -6), (-9, 7), (12, 14), (-4, 24)]` and default pads `(3, 2, 2, 1, 1)`.
   - Block time: `4 + ceil(d/3)` computed using integer tenths `4 + (-(-int(round(d * 10)) // 30))` to prevent float precision bugs.
   - Energy consumption: `12.0 + 1.0 * d_km` (% SoC / kWh, since usable battery = 100 kWh).
   - Piecewise-linear charging curve: `2.0 * mult` %/min below 80% SoC; `(2.0 / 3.0) * mult` %/min in `[80%, 100%]`, capped at 100%.
   - Stint merging rule (Scenario §5): If a 5-minute post-landing stint at vertiport `v` is immediately followed by a pre-departure stint at the same vertiport `v` (`prev.end == next.start`), merge them into a single continuous `STINT` activity.
2. **Independent Constraint Checker (`auditor.py`):**
   - Must NOT share internal state or helper classes with `env.py` or `jit_implementation.py`.
   - Takes raw output logs (`schedule.csv`, `decisions.csv`, `requests.csv`, and `Config`) and independently verifies from scratch:
     a) Every `ACCEPT` decision has exactly one matching revenue `FLIGHT` in `schedule.csv` within `[earliest_dep, latest_dep]`; zero accepted-then-failed requests.
     b) No activity for request `R_i` starts before `reveal_time = max(0, earliest_dep - 30)`.
     c) Temporal & spatial continuity for each aircraft `A0..A7` (starts at initial position at `t=0` with `90%` SoC; every flight is preceded and followed by a valid pad stint of `>= 5` min; origin of activity `n+1` equals destination of activity `n`; no overlapping intervals; all activities end `<= 360`).
     d) Exact SoC trajectory reconstruction: verify `SoC >= 20.0 - 1e-7` at every landing and `SoC <= 100.0 + 1e-7` everywhere.
     e) Minute-by-minute pad occupancy across `[0, 360)` for `V0..V4` never exceeds `cfg.pads[v]`.

### AGENT 2: RL & Operations Research Scientist (Problem B - Formulation)
**Responsibility:** Formulate the MDP/SMDP state space, macro-action space, hard safety shield, and reward engineering.
1. **Why Event-Driven Macro-Action SMDP:**
   - Decisions occur sequentially as requests are ordered by `(earliest_dep, id)`.
   - Committed plans are immutable (`Scenario` & `jit_implementation.py` Rule 2).
2. **Macro-Action Space & Hard Action Masking (Safety by Construction):**
   - Instead of raw minute-level actions, define a candidate plan generator at each request step `req`:
     - Action `0`: `REJECT` (always feasible / unmasked).
     - Actions `1..8`: Assign Aircraft `k` (`0..7`) using **JIT Charging** (exact `plan_for_aircraft` logic from `jit_implementation.py`).
     - Actions `9..16`: Assign Aircraft `k` (`0..7`) using **Opportunistic Fast Charging (Charge-to-80% / Extended Stint)**: if Aircraft `k` has slack time before departure and pad capacity at the origin/current vertiport is free, extend the charging stint up to `max(min_required_target, 80.0)` SoC (taking advantage of the fast `2.0%/min` charging regime below 80% SoC without delaying departure `D` or blocking scarce pads).
     - Actions `17..24`: Assign Aircraft `k` (`0..7`) with **Delayed Departure (`D_late`)**: depart at the latest feasible window or after peak pad congestion clears, allowing fuller charging.
   - **Safety Enforcement:** Explain rigorously why **Hard Action Masking** (combined with Candidate Plan Verification) is superior to Soft Reward Penalties (which fail under distribution shift and exploration) and Post-Hoc Projection Shields (which distort policy gradients).
3. **Feature-Rich State Vector (`obs`):**
   - **Request Features (Normalized):** One-hot origin (5), one-hot dest (5), `earliest_dep / 360`, `(latest_dep - earliest_dep) / 15`, `dist_km / 40`, `revenue / 200`, direct profit margin `(revenue - 1.5*d - 0.3*energy(d)) / 100`, time-to-peak `(earliest_dep - 150) / 150`.
   - **Per-Aircraft Context & Plan Delta Features (8 aircraft):** Current location one-hot (5), `max(0, free_from - reveal) / 60`, `soc / 100`, feasibility mask for this request (binary), required `deadhead_km / 40`, direct net profit of assigning aircraft `k` (accounting for deadhead km and deadhead energy cost), post-assignment landing SoC `/ 100`, destination origin-weight `ORIGIN_WEIGHTS[dest]`, and destination pad scarcity `1.0 / pads[dest]`.
   - **Network Pad Congestion Features:** For each vertiport `v in 0..4`, pad utilization in `[reveal, min(360, reveal + 60)]` and `[min(360, reveal + 60), min(360, reveal + 120)]`.
4. **Reward Design & Ablation:**
   - **Primary Reward ($R_{\text{shaped}}$):** Immediate economic profit contribution of the chosen action PLUS potential-based state valuation:
     $$r_t = \underbrace{\mathbb{I}(\text{accept}) \cdot \left(\text{rev} - 1.5(d_{\text{rev}} + d_{\text{dh}}) - 0.3(E_{\text{rev}} + E_{\text{dh}})\right)}_{\text{True Accounting Profit}} + \alpha_{\text{soc}} \Delta \text{SoC}_{\text{fast}} - \alpha_{\text{pad}} \text{PadCongestion}(v_{\text{dest}}, t_{\text{arr}})$$
     where terminal return matches true episode profit during evaluation.
   - **Rejected Reward Variant (Required by Rubric):** Document and empirically compare against a *Naive Sparse / Terminal-Only Profit Reward* or *Unpenalized Acceptance Bonus Reward* (where giving `+B` for every served request causes the agent to accept unprofitable long-deadhead flights that starve high-margin peak requests).

### AGENT 3: High-Performance ML Engineer (Training & CPU Optimization)
**Responsibility:** Guarantee convergence in **$\le 15$ minutes on a standard Laptop CPU** (well under the 45-minute cap).
1. **Two-Stage Hybrid Training Pipeline:**
   - **Stage 1: Lookahead / Rollout Oracle Imitation Warm-Start (Behavioral Cloning):**
     - Generate 500–1,000 synthetic days using `generate_requests`.
     - Instead of cloning pure `Greedy-JIT`, clone an **M-Step Rollout / Value-Guided Teacher** (or train a lightweight MLP/dueling Q-network on Monte Carlo rollouts that compares `REJECT` vs. `ACCEPT (aircraft k, charge_mode m)` by running fast `Greedy-JIT` rollouts to the end of the day!).
     - *Crucial Insight:* Because `run_day` in `jit_implementation.py` takes `< 1.5 ms` per day in Python, rolling out all feasible macro-actions at decision step `t` using `Greedy-JIT` as the base policy (Policy Improvement / Rollout RL, Bertsekas) or training a Value Network $V_\theta(s)$ + Maskable PPO warm-started from BC is blazingly fast and guarantees strictly outperforming `Greedy-JIT`!
   - **Stage 2: Maskable PPO / Double-DQN Fine-Tuning:**
     - Fine-tune the policy network (2-layer MLP `128x128` with `ReLU` and invalid-action logit masking `-1e9`) across seeds `0..999` with domain randomization on `demand_mult` $\in [0.8, 1.3]$.
     - Log wall-clock training time, hardware specs (`platform`, `cpu_count`), learning curves, and save portable weights (`.pt` or `.npz`).
